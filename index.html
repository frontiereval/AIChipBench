Abstract

A language-model decoder carries state between decoding steps, and in hardware a wrong state update can leave the current token correct and corrupt the output several tokens later, so a design can pass output tests and still be wrong. AIChipBench asks what LLM coding agents need to build such hardware correctly.

Agents implement quantized Qwen3.5, Gemma 3, Gemma 4, and Llama 3.2 decoders in synthesizable register-transfer-level (RTL) code against an executable integer reference that specifies the outputs and the stored state at every decoding step. They debug against public tests under fixed budgets; their frozen designs are graded on held-out token sequences, resets, memory stalls, and synthesis, and a second track asks them to speed up a correct design at nearly fixed area.

Across 9,136 attempts by four coding agents, the difficulty lies in stored state. Feedback that points to the first state mismatch raises acceptance over output-only feedback in all 12 agent–task cells of a matched study, by 25.0 to 46.9 percentage points, and halves the agent-hours per accepted design. Regraded on new sequences and conditions, 45 of 69 accepted designs fail within the 32 steps their tests required. More than a third of attempts to speed up a correct design end without one. An overall score ranks Sol 5.6 and Fable 5.1 above Astra 6 and Opus 5.5, and both halves of the instances give this order in all 200 random splits. Hardware agents therefore need debugging feedback that exposes stored state, and their benchmarks need final tests well beyond the development cases.

Two tracks, one evaluator

An agent is a language model run in a tool-using harness: it inspects files, writes and revises hardware code, runs lint, simulation, and synthesis, reads test feedback, and submits a design within caps on wall time, tool calls, and output tokens.

01 / Correctness

Build a decoder.

The agent starts from module interfaces or a working accelerator scaffold and implements a quantized decoder in RTL. Twelve tasks cover seven targets from the Qwen3.5, Gemma, and Llama 3.2 families.

02 / PPA

Speed up a correct design.

The agent starts from a correct reference design and must raise throughput by at least 5% with at most 2% more LUTs while every check still passes. Four targets, on an AMD Alveo U250 FPGA at a 126 MHz target clock.

03 / Evaluation

Frozen, held-out grading.

An integer oracle gives the exact outputs and stored state at every transaction. A submitted design is frozen and accepted only if it matches the oracle on held-out sequences, resets, and memory stalls, synthesizes, and leaves protected files intact.

Findings

Five results recur across the two tracks and the diagnostic studies.

  1. Agents adapt a scaffold more reliably than they build a full-size decoder from interfaces.On four full-size targets, 408 of 704 attempts from a scaffold are accepted, against 239 from interfaces.
  2. Agents do much better when told where state diverges.Feedback that locates the first state mismatch raises acceptance over output-only feedback in all 12 agent–task cells, by 25.0 to 46.9 points, and lowers the cost per accepted design from 13.4 to 6.5 agent-hours.
  3. Passing a test suite does not establish exactness.148 designs pass every public test and fail final acceptance. When frozen submissions are regraded, 45 of 69 accepted designs fail a new sequence or condition within the 32 steps their tests required.
  4. Longer horizons lower acceptance, and the budget binds.At the 1× budget, pooled acceptance falls from 252 to 115 of 288 attempts between one and 16 required decoding steps, and 489 of 1,888 correctness-track attempts end at a cap without submitting.
  5. Optimization often ends without a correct design.571 of 1,536 PPA attempts end without a correct design, although each started from one that passed every gate.
